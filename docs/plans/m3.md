# M3 plan: audit reports

Status: approved to proceed without a review stop, as for M1 and M2 (Flavio asked on 2026-09-26 for M1 to M4 to be built overnight). Decisions that would normally be questions are listed under "Decisions taken without review".
Date: 2026-09-27

## Goal

Give an auditor evidence they can verify without trusting us: signed packages with a hash for every file, a log of every access, and an audit trail whose tampering can be detected and located.

Acceptance, from the brief: a generated package verifies; changing one byte makes verification fail; a broken audit chain is detected and located.

## Scope

### Report types and renderers

The six report types from the brief, each built from stored measurements, definitions, batches and registers, never from live collection:

1. Control evidence package: one control, one period.
2. Framework period report: chosen requirements of one framework for a period.
3. Metric reproducibility report: definition version, query, input batch hashes, calculation record and result, with the batches included so the number can be recomputed.
4. Risk committee pack: one page of key risk indicators with status, owner and action.
5. Management report: KPI trends against baseline and target.
6. Exceptions register export with age, root cause and expiry.

Renderers are plugins in the `dsec_metrics.renderers` group: `pdf` (Jinja2 and WeasyPrint), `xlsx` (openpyxl), `csv` and `json` (standard library). The PDF has a cover page with the "Prepared for" line and date, scope and period, method, summary counts by status, one section per control, a chain-of-custody section, an appendix with the metric definitions used, a table of contents and page numbers, and prints the signing key's fingerprint.

### Package format

A ZIP with `report.pdf`, `report.xlsx`, an `evidence/` folder (the record batches as JSON, named by hash, plus CSV exports), `manifest.json` and `manifest.sig`.

- The manifest lists every file with its SHA-256, size, source, collection time and the measurement or evidence record it belongs to, plus the report type, scope, period, generator version, generation time, who generated it and the public key fingerprint.
- `manifest.sig` is a detached Ed25519 signature over the exact bytes of `manifest.json`.
- ZIP entries have fixed timestamps and order, so the same inputs give the same archive apart from the generation time.
- `dsec-metrics verify package.zip [--public-key key.pem]` checks the signature, every listed hash and size, that no file is missing, and that no unlisted file is present. It exits non-zero on any mismatch and says which file failed. It needs no database and no network.

### Signing key

- Ed25519 through the `cryptography` library. The private key is a PEM file read from a Docker secret (`/run/secrets/report_signing_key`); `make dev-secrets` creates one for development and `dsec-metrics keys generate` creates one for production.
- The fingerprint is the SHA-256 of the raw public key, shown in hex in the PDF, the manifest and the audit room.
- `GET /api/reports/public-key` publishes the PEM public key so auditors can pin it.

### Roles and the auditor

The brief's full RBAC is M5, but M3 needs the auditor role, so roles arrive now in their simplest form:

- Users get roles from the brief's list (`admin`, `metric_owner`, `reviewer`, `viewer`, `auditor`, `service`). The development admin is `admin`.
- The policy module gains role policies. Existing read routes need a staff role (anything except `auditor`). Generating reports needs `admin`, `metric_owner` or `reviewer`. The audit log needs `admin`.
- An auditor grant names a user, frameworks, a period, and an expiry. Auditors see only packages whose framework and period fall inside an unexpired grant, through the audit room screen and time-limited links. Everything else returns 403.
- `dsec-metrics users grant-auditor` creates a local auditor with a grant (development mode only, like all local accounts; OIDC groups replace this in M5).
- Every package download, by anyone, is written to the audit log with the user, package, link and address.

### Audit log

- An `audit_events` table: sequence number, time, actor, action, target, details, the previous entry's hash, and this entry's hash (SHA-256 over the canonical JSON of the other fields).
- Appends take a transaction-level advisory lock so the chain stays linear with several API and worker processes.
- A database trigger rejects UPDATE, DELETE and TRUNCATE on the table. The application never needs them.
- Events: sign-in, sign-out, sign-in failure, definition sync, collection runs, report generation, link creation, downloads, auditor grants. Each is also written to stdout as a JSON line for the SIEM, as sign-in events already are.
- `dsec-metrics audit verify` recomputes the chain and reports the first broken link (sequence number and which check failed), exiting non-zero.
- Admins see the log in the admin audit viewer, with its verification status.

### Screens

- Reports: pick a type, scope and period, generate, then download or create an auditor link.
- Audit room: the auditor's landing page with their frameworks, periods, packages and access log.
- Audit log viewer for admins.

### Tests

- Unit: manifest building, signing and verifying; a one-byte change in any file, the manifest or the signature fails verification; a missing or extra file fails; canonical hashing of audit events.
- Integration: each report type builds from the demo data and verifies; the audit chain detects an edited row, a deleted row and a reordered row (with the trigger disabled for the test) and names the first broken sequence number; the trigger blocks UPDATE and DELETE; auditor access is limited to the granted framework, period and expiry; every download is logged.
- Playwright: generate a report, download it, and verify it with the CLI; the audit room as an auditor; axe on the new screens.

## Decisions taken without review

1. WeasyPrint needs Pango and its libraries. The distroless base has none, so the image build copies exactly the shared libraries WeasyPrint loads (found with `ldd` in the build stage) and one font family into the final image. Still no shell, still non-root. ADR-0010 records this and its trivy results. If trivy reports a high or critical finding in those libraries with no fix, I stop the PDF renderer, ship XLSX, CSV and JSON, and raise it.
2. Packages are stored in Postgres (`report_packages`, bytea) rather than on a volume: one place to back up, and the root filesystem stays read-only.
3. Roles arrive in M3 in minimal form (a roles column and role policies) because the auditor role needs them. M5 maps OIDC groups onto the same roles.
4. Time-limited links are tokens (256-bit, only the hash stored) tied to one auditor, one package and an expiry no later than the grant's. The auditor still has to sign in.
5. The audit chain uses a trigger for append-only rather than a separate database role, because Compose runs one database user. M5's hardening guide adds a separate role that owns the table.

## Risks

- WeasyPrint's native dependencies are the largest addition to the image so far; see decision 1.
- PDF rendering time for the framework period report on 40 controls. Target under 10 seconds; if it is slower, generation moves to the worker with a job row the UI polls.
- Deterministic ZIPs depend on fixed entry order and timestamps; tests check that rebuilding from the same inputs gives the same file hashes.

## Outcome

Built as planned, with one change to decision 1. Copying Pango and its libraries into the image worked, but trivy then reported 12 high-severity findings with no fixed version (util-linux through GLib, and Expat through Fontconfig). They look unreachable from report rendering, but suppressing them needs your approval (ADR-0005), so the image does not ship them yet. Packages built in the default image carry `report.html` in place of `report.pdf`; everywhere Pango is present (developer machines, the CI test job) they carry the PDF. ADR-0010 lists the findings and three ways forward for you to choose from.

Other things that came up:

- `dsec-metrics reproduce` recomputes a reproducibility package's number from its own evidence with the same evaluator. It was not in the plan, but it makes the reproducibility report checkable rather than just readable.
- The e2e suite verifies downloaded packages with Node's crypto and a small ZIP reader, independent of the Python verifier.
- `make dev-secrets` creates the signing key with OpenSSL 3 when it can; macOS ships LibreSSL, which cannot make Ed25519 keys, so `make signing-key` creates it with the app image instead.
- `openpyxl` and `weasyprint` ship no type information; they are listed with `testcontainers` under the mypy `ignore_missing_imports` override rather than adding stub packages (a new dependency).

What ran before calling M3 done:

- `make ci`: ruff, mypy `--strict`, ESLint, tsc, Prettier, pytest (363 tests; core 98 percent, overall 96 percent coverage), Vitest (59 tests), bandit, semgrep, pip-audit, osv-scanner, gitleaks, zizmor, both image builds with trivy, Playwright (20 tests, axe on every new screen) and the strict MkDocs build.
- Acceptance: every report type builds and verifies (`tests/integration/test_reports.py`); changing one byte in a file, the manifest or the signature fails verification (`tests/unit/test_package.py`, `tests/integration/test_reports_cli.py`, and the e2e test that checks packages with Node's crypto); edited, deleted and reordered audit entries are detected and the first broken entry is named (`tests/integration/test_audit.py`).
