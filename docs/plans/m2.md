# M2 plan: dashboards

Status: approved to proceed without a review stop, as for M1 (Flavio asked on 2026-09-26 for M1 to M4 to be built overnight). Decisions that would normally be questions are listed under "Decisions taken without review".
Date: 2026-09-27

## Goal

Show the measured results to each audience, with every number traceable to its definition, measurement and source batch.

Acceptance, from the brief: the Playwright and axe suites pass; the performance targets hold on the sample dataset (dashboards render in under 1.5 seconds; dashboard API calls stay under 300 ms at p95).

## Scope

### API (read-only)

All routes use the `authenticated` policy. Roles and business-unit scoping arrive in M5; the routes are written so the M5 scope filter has one place to go (a `Scope` passed to every query helper, which is "everything" until then).

| Route | Returns |
| --- | --- |
| `GET /api/metrics` | the catalog with each metric's latest overall value and status |
| `GET /api/metrics/{metric_id}` | the current definition, its version history and threshold bands |
| `GET /api/metrics/{metric_id}/measurements` | history for a slice (`periods`, dimension filters), plus the slices available on the latest date |
| `GET /api/measurements/{measurement_id}` | one measurement with its calculation record, definition version and input batches |
| `GET /api/batches/{sha256}` | batch metadata (collector and version, instance, query, params, times, record count, redaction summary) and a page of redacted records |
| `GET /api/controls` | controls with a rolled-up status (the worst status of their metrics) and counts of open exceptions and findings |
| `GET /api/controls/{control_id}` | requirements with short titles, metrics with status, evidence sources with their latest batch, exceptions and findings |
| `GET /api/exceptions` | the exceptions register with age, days to expiry and root cause, filterable |
| `GET /api/findings` | the findings register, filterable |
| `GET /api/dashboards` | the dashboards and their audiences |
| `GET /api/dashboards/{dashboard_id}` | the layout with every widget's data resolved in one response |

Dashboard responses are built from stored measurements only (pre-aggregated by the evaluator), never from raw batches, except the exceptions-aging widget, which reads the latest exceptions register batch.

Dimension filters (`business_unit`, `application`, `environment`, `region`) are query parameters. A widget uses the measurement slice that matches the filter. When a metric is not grouped by the filtered dimension, the widget shows the overall value and says it is not broken down that way, rather than showing a number that looks filtered but is not.

### Registers

The exceptions and findings registers come from collector data, like everything else. A new definition kind, `content/registers/*.yaml`, names the source for each:

```yaml
id: exceptions
source: {collector: sample, query: open_exceptions}
```

The register views read the latest successful batch for that source, validate each record against a documented field list (the data model's fields for exceptions and findings), skip and count invalid records, and link every row to its batch hash.

### Rate and size limits

- A fixed-window rate limit on every route, stored in Postgres (ADR-0001 rules out Redis): per signed-in user when there is a session cookie, per client address otherwise. Defaults: 600 requests a minute per user, 120 a minute per address for unauthenticated requests. Over the limit returns 429 with `Retry-After`. The worker purges old windows.
- Request bodies stay capped at 1 MB at the proxy; the API also rejects bodies over 1 MB, so the limit holds without Caddy.
- The authorization test gains a check that every route passes through the limiter.

### Front end

- Screens: overview with an audience switcher, the three audience dashboards, metric detail, controls list, control detail, exceptions.
- Metric detail: current value and status, threshold bands, 12-period history, dimension breakdown, the source batches used (with a record viewer), the definition and its version history.
- Widgets: `stat`, `trend`, `bar`, `table`, `rag_list`, `heatmap`, `exceptions_aging`, `findings_burndown`. Every number links to the metric detail for that measurement.
- Status always shows an icon and a label with the colour: green check, amber triangle, red octagon, grey question mark.
- Charts: Apache ECharts through echarts-for-react, a colourblind-safe palette (Okabe-Ito), one y-axis, an accessible name on each chart, and a "View as table" toggle.
- Tables: TanStack Table with sortable headers that announce their sort state.
- Filter bar for the four dimensions; filter state lives in the URL so views can be shared.
- Skeleton loading states; empty states that say what to do next; the print stylesheet from M0 extended to dashboards.
- Light and dark mode for every screen, including charts.

### Tests

- API: integration tests per route against the demo dataset, the authorization walk for every route, rate limit tests, and a performance test that loads the 12-month demo and requires p95 under 300 ms for each dashboard call.
- Web: Vitest for widgets, status badges, the router and the table toggle.
- Playwright: sign in, each audience dashboard, drill-down from a dashboard number to metric detail to a source batch, controls and exceptions screens, theme switching, axe on every screen in both themes, and a render-time check of under 1.5 seconds per dashboard.

## Decisions taken without review

1. Routing is a small in-house router (about 80 lines over the History API) rather than a routing library. The brief names no router, and the app has six screens.
2. Registers are a new definition kind under `content/registers/`, for the same reason collector instances are: definitions as code.
3. Rate limits use Postgres, per ADR-0001. If measured cost matters, a per-process token bucket can sit in front of it later.
4. New web dependencies, all named in the brief: `echarts`, `echarts-for-react`, `@tanstack/react-table`. If `echarts-for-react` does not support React 19, a 40-line wrapper over `echarts` replaces it and the package is not added.
5. No new Python dependencies.

## Risks

- ECharts is large. It is imported through `echarts/core` with only the chart types used, and dashboards load it lazily.
- ECharts writes inline styles through the DOM API. The CSP forbids inline style attributes set through markup; if ECharts trips it, the e2e console check fails and I fix it there rather than loosening the CSP.
- Per-request rate-limit writes add database load. The performance test covers it.
