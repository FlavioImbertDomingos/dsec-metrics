Decisions that would normally be questions are made conservatively and listed under "Decisions taken without review" so they can be reversed.
Date: 2026-09-26

## Goal

Turn YAML definitions into versioned, reproducible measurements.

Acceptance, from the brief: `dsec-metrics demo` followed by `dsec-metrics status` prints the metric catalog with values and statuses; evaluator property tests pass; the card-number redaction test passes.

## Scope

### Definition language (`dsec_metrics.core.definitions`)

Pydantic v2 models, strict (`extra="forbid"`), for the four definition kinds, matching the examples in the brief:

- Framework pack: `id`, `name`, `version`, `source_url`, `requirements` (`ref`, `short_title`, optional `text` for public-domain frameworks only).
- Metric: `id`, `name`, `type` (`kpi`, `kri`, `kci`), `question`, `owner`, `audience`, `source` (`collector`, `query`, `params`), `evaluation`, `frequency`, `thresholds` (with per-dimension overrides), `action_when_red`, `frameworks`, `baseline`, optional `target` and `unit`, `approved_by`, `review_by`.
- Control: `id`, `name`, `owner`, `description`, `requirements`, `metrics`, `evidence`.
- Dashboard: `id`, `title`, `audience`, `refresh`, `layout` of typed widgets.
- Collector instance (new file kind, `content/collectors/*.yaml`): `id`, `plugin`, `config`, `schedule`. The brief's data model has collector instances with config, secret references and a schedule; keeping them as YAML keeps "definitions as code" true for them as well.

Evaluation kinds: `count`, `sum`, `ratio`, `percentage`, `median`, `percentile`, `age_over`, `sla_breach`, `latest_value`. Filters are `{field, op, value}` with `op` in `eq`, `ne`, `gt`, `gte`, `lt`, `lte`, `in`, `not_in`, `exists`, `missing`. `group_by` accepts only the four dimensions (`business_unit`, `application`, `environment`, `region`).

Thresholds: bands `green`, `amber`, `red`, each a set of bounds (`min`, `max` inclusive; `above`, `below` exclusive). The first band that matches wins, in the order green, amber, red; a value that matches none is red. Overrides replace bands for slices whose dimensions match.

Cross-reference validation (`dsec-metrics validate`): framework references resolve to a pack requirement; control metric ids exist; dashboard metric ids exist; metric sources name a configured collector instance and a query that plugin offers.

### Versioning

The definition hash is SHA-256 over canonical JSON (sorted keys, no insignificant whitespace, UTF-8). Syncing content stores each distinct hash as a new row with an incrementing version number; nothing is overwritten. Measurements record the definition hash and version.

### Evaluator (`dsec_metrics.core.evaluator`)

A pure function: metric definition + input batches + `as_of` (+ the previous period's values, and the time of the last successful collection) produce measurements. It computes the overall value and one value per `group_by` slice, the status, change from the previous period, change from baseline, distance to target, and a `calculation` record (inputs, filtered record count, formula, intermediate numbers) that M3's reproducibility report will print.

`unknown` status: no input batch, or the last successful collection is older than twice the metric's frequency.

Tests first: Hypothesis property tests for every evaluation kind and every threshold shape (determinism, invariance to record order, filter semantics against a reference implementation, band ordering, override precedence).

### Redaction (`dsec_metrics.core.redaction`)

Pure. Drops fields the collector marks sensitive plus a global list (`cvv`, `cvv2`, `cvc`, `pin`, `pin_block`, `track1`, `track2`, `track_data`, `password`, `secret`), masks any 13 to 19 digit sequence (spaces or dashes allowed between digits) that passes the Luhn check to first six and last four, walks nested lists and objects, and returns a summary of what changed. Runs in the worker before anything is stored.

### Plugin SDK and collectors

- `plugins/sdk`: `Collector` base class as in the brief, `CollectorConfig`, `RecordBatch`, `ConnectionResult`, `SecretResolver` with `env://` and `file://` providers, entry-point registry for the four groups, and a contract-test helper.
- `file` collector: CSV and JSON files under a configured base directory, one query per file. Path traversal outside the base directory is refused.
- `sample` collector: deterministic synthetic data for 12 months, three business units and 40 controls from a seeded `random.Random`, with an evidence-request spike before an audit and metrics that turn red and recover.

### Storage (migration 0002)

Tables `definitions`, `collector_instances`, `collection_runs`, `record_batches`, `measurements`. Record batches keep the redacted records inline as JSONB in M1 (`storage_ref = "db:inline"`); object storage can come later. Measurements are insert-only with a unique key on metric, definition hash, `as_of` and dimension slice.

### Services, CLI and worker

- `dsec_metrics.pipeline`: load and validate content, sync definitions, run a collection (collect, redact, hash, store), evaluate metrics for an `as_of` date.
- CLI: `validate`, `collect`, `evaluate`, `demo`, `status`.
- Worker: one schedule per collector instance in a `schedules` table, claimed with `SELECT ... FOR UPDATE SKIP LOCKED`, plus the M0 heartbeat. See decision 2 for why this is not APScheduler.

### Default content

- Framework packs: NIST CSF 2.0 (functions and categories with their official titles, plus the subcategories the default controls reference), PCI DSS v4.0.1, SOC 2 TSC and ISO/IEC 27001:2022 Annex A, each with only the requirement IDs the default controls use and short titles we wrote.
- The 16 data security metrics from the brief.
- 40 controls across key management, data protection, access, vulnerability and audit readiness.
- The three audience dashboards (layouts only; rendering is M2).

## Decisions taken without review

1. PyYAML (`yaml.safe_load` only) parses definitions. The brief requires YAML definitions but names no parser. Flagged for approval; replacing it is mechanical.
2. No APScheduler (changed during the build; ADR-0007). The plan was APScheduler 4.0.0a6 with its JSON serializer. pip-audit then failed on PYSEC-2026-282 (CVE-2026-31072): APScheduler's JSON and CBOR serializers import and instantiate classes named in stored data, in every released version, with no fix. Anyone able to write to the job store could run code in the worker. The brief forbids weakening a gate, so the dependency was removed instead of suppressed. The replacement is about 150 lines: a stdlib five-field cron parser in `core/cron.py` with property tests, and a `schedules` table that stores a job name from a fixed registry and string arguments. This drops APScheduler, sniffio, attrs, tenacity and tzlocal from the lock file. The brief's table names APScheduler, so this needs your confirmation; switching back is possible if upstream fixes the serializers.
3. Collector instances are YAML files under `content/collectors/`.
4. Percentiles use the nearest-rank method, which is deterministic and easy for an auditor to recompute by hand.
5. Framework packs contain the requirements the default controls use, not the whole standard. NIST CSF 2.0 categories are complete.

## Risks

- APScheduler 4 was an alpha with a missing dependency declaration. It turned out to have an unfixed deserialization CVE, and the fallback above is now the design.
- An in-house cron parser can disagree with other cron implementations at the edges. It supports numbers, ranges, steps and lists only, rejects everything else, and is checked against an independent oracle by Hypothesis.
- The sample data is synthetic by design; realistic-looking patterns must not be mistaken for benchmarks.
