### Python package skeleton

`src/dsec_metrics/` with the module layout from the brief (`core`, `plugins/sdk`, `worker`, `api`, `reports`, `cli`), each with a docstring stub so the docs site and import-boundary test have something to check. Only `api`, `worker`, `cli` and a small `config` module get real code in M0.

- `config`: settings read from environment variables and `*_FILE` variables (for Docker secrets), validated by Pydantic. `DSEC_MODE` is `development` or `production`.
- Startup guard: the app refuses to start when `DSEC_MODE=production` and local accounts are enabled. Tested.
- Structured JSON logging to stdout from day one, so the SIEM feed shape is set before M3.
- Import-boundary test: a pytest test that parses every module under `core/` with `ast` and fails on imports of other `dsec_metrics` packages or of I/O libraries (sqlalchemy, httpx, socket, subprocess and similar). Standard library only, no import-linter dependency.

### API

FastAPI app with these routes, all under `/api`:

| Route | Access | Purpose |
| --- | --- | --- |
| `GET /api/healthz` | public | liveness, no dependencies |
| `GET /api/readyz` | public | readiness, checks the database |
| `GET /api/meta` | public | product name and version |
| `POST /api/auth/login` | public | dev-mode local sign-in |
| `POST /api/auth/logout` | signed in | ends the session |
| `GET /api/me` | signed in | current user and CSRF token |

Authorization starts the way it will continue. There is one `policy` module, and every route declares either a required permission or an explicit `public` marker. A test walks `app.routes` and fails if any route has neither, and fails if any route lacks at least one allowed and one denied test case in the route-auth test table. This is the "CI fails if any API route lacks an authorization test" rule from the brief, built now while there are six routes instead of sixty.

Dev authentication (question 11):

- Local accounts, only in development mode, with Argon2id password hashes.
- Server-side sessions in Postgres. The browser gets an opaque random token in a `__Host-dsec_session` cookie (Secure, HttpOnly, SameSite=Strict, Path=/). The database stores only the SHA-256 of the token. Idle timeout 30 minutes, absolute timeout 8 hours, both configurable.
- CSRF: a per-session synchronizer token returned by `/api/me` and required in an `X-CSRF-Token` header on every unsafe method, plus an `Origin` check.
- Login throttling per username and per source address, stored in Postgres (no Redis).
- Sign-in and sign-out events go to the JSON log. The hash-chained audit table is M3.

Database: SQLAlchemy 2 and Alembic with a first migration for `users` and `sessions`. A one-shot `migrate` compose service runs `alembic upgrade head` before api and worker start.

### Worker

A placeholder process that starts, checks the database, logs a heartbeat every 30 seconds and writes a heartbeat file to its tmpfs for the health check. APScheduler is not needed until M1, so it stays out of M0 (see risks for the APScheduler 3 vs 4 question I will raise in the M1 plan).

### CLI

Typer app with `dsec-metrics version` and `dsec-metrics dev create-user`. The second refuses to run in production mode. The compose `migrate` step also creates `dev-admin` from a Docker secret file if the user does not exist.

### Web

Vite, React, TypeScript strict, Tailwind, shadcn/ui primitives, TanStack Query, lucide-react.

- Two screens: sign-in and a placeholder home page inside the app shell (top bar with product name, user menu, theme toggle).
- Light and dark mode from the first screen: follows the system setting, with a manual override kept in localStorage. The theme is applied by a small external script loaded before the app bundle, because the CSP allows no inline scripts.
- Inter self-hosted (no runtime call to a font CDN, so it works air-gapped), tabular figures on, 8 px spacing scale, 12 px card radius, hairline borders, neutral grays and one accent color as CSS variables.
- Vitest unit tests for the shell and the auth hook; Playwright end-to-end test for sign-in, sign-out and theme switching, with axe-core in both themes.

### Docker Compose

`compose.yaml` (location is question 4) with these services:

| Service | Image | Notes |
| --- | --- | --- |
| postgres | official `postgres:16`, pinned by digest | password from a Docker secret via `POSTGRES_PASSWORD_FILE`, data volume, `pg_isready` health check |
| migrate | app image | one-shot: Alembic upgrade, create dev user |
| api | app image | uvicorn, health check runs `dsec-metrics health api` in exec form (there is no shell or curl in the image) |
| worker | app image | same image, different command |
| web | our Caddy image | TLS, security headers, serves the built front end, proxies `/api` to api |

Networks: `edge` (only web publishes a port) and `backend` with `internal: true` (web, api, worker, postgres). The worker will need an egress network for collectors in M4; M0 has no outbound traffic at all.

Hardening on every service we build: non-root user, `read_only: true`, tmpfs for `/tmp`, `cap_drop: [ALL]`, `no-new-privileges`, memory and CPU limits, restart policy. Caddy listens on 8443 inside the container and the host maps 443 to it, so it needs no `NET_BIND_SERVICE`.

TLS: Caddy `tls internal` for `localhost` in development, with the root CA in a named volume. The README explains how to trust that root or accept the browser warning. `DSEC_HOSTNAME` and operator-supplied certificates come with the deployment section (question 5).

Secrets: `.env.example` is committed, `.env` is ignored. `make dev-secrets` writes random values into `deploy/compose/secrets/` (git-ignored, mode 600) for the Postgres password and the dev admin password, and prints the dev admin password once.

A `compose.dev.yaml` override with bind mounts, uvicorn reload and the Vite dev server comes along for day-to-day work. It is not used for acceptance.

### Container images

Two images, both multi-stage, non-root, read-only root filesystem and no shell in the final stage (question 7 and question 8):

- `dsec-metrics` (api, worker, migrate, cli): uv builds the virtual environment from `uv.lock` with hashes; Python is the python-build-standalone 3.12 build that uv installs, copied onto `gcr.io/distroless/cc-debian12:nonroot`. Bytecode compiled at build time.
- `dsec-metrics-web`: the front end is built with pnpm in a Node stage; the static Caddy binary from the official Caddy image is copied with the assets and `Caddyfile` onto `gcr.io/distroless/static-debian12:nonroot`.

All base images are pinned by digest, and Dependabot updates the digests.

### Caddy configuration

- HSTS (`max-age=31536000; includeSubDomains`), `X-Content-Type-Options: nosniff`, `Referrer-Policy: no-referrer`, `Permissions-Policy` with everything off, `Cross-Origin-Opener-Policy: same-origin`, `Cross-Origin-Resource-Policy: same-origin`, frame-ancestors none.
- CSP: `default-src 'none'; script-src 'self'; style-src 'self'; img-src 'self' data:; font-src 'self'; connect-src 'self'; base-uri 'none'; form-action 'self'; frame-ancestors 'none'`.
- Request body size limit at the proxy (1 MiB for `/api`, adjustable per route later).
- Server header removed. Access logs as JSON to stdout.

## CI design

### Workflows

`ci.yml` runs on pull requests and pushes to `main`. All jobs are required status checks.

| Job | Tools | Fails on |
| --- | --- | --- |
| python-lint | ruff check, ruff format --check, mypy --strict (src and tests) | any finding |
| python-test | pytest with Testcontainers Postgres, pytest-cov | any failure; coverage under 80% overall or under 90% for `core` |
| web-lint | eslint (`--max-warnings 0`), tsc --noEmit --strict | any finding |
| web-test | vitest with coverage | any failure |
| sast | bandit, semgrep (`p/owasp-top-ten`, `p/python`, `p/typescript`, `p/react`, `p/dockerfile`, `p/secrets`) | bandit per question 16; semgrep any ERROR |
| deps | pip-audit on the locked set, osv-scanner on `uv.lock` and `pnpm-lock.yaml` | high or critical |
| secrets | gitleaks over full history | any finding |
| workflows | zizmor on `.github/` | any finding at medium or above |
| images | build both images, trivy image scan, trivy config scan of the Dockerfiles, CycloneDX SBOM from trivy uploaded as an artifact | high or critical |
| e2e | build images, `docker compose up -d --wait`, Playwright with axe-core against `https://localhost` | any failure or axe violation |
| docs | `mkdocs build --strict` | any warning |

`release.yml` runs on tags `v*`: build both images, push to GHCR by digest, sign with cosign keyless (GitHub OIDC), attach the CycloneDX SBOM as a signed attestation, generate SLSA provenance (question 13), and create a GitHub release with the SBOMs and checksums. The release job re-runs the full CI suite first.

`docs.yml` publishes the site to GitHub Pages from `main` once the repository is public.

`dependabot.yml`: uv, npm (pnpm), Docker (base image digests), GitHub Actions. Weekly, grouped by ecosystem, with security updates ungrouped so they arrive right away.

### Workflow hardening

- `permissions: {}` at the top of every workflow; each job asks only for what it needs (`contents: read`, plus `packages: write` and `id-token: write` in release, `pages: write` in docs).
- Every action pinned to a full commit SHA with the version in a comment. Every tool pinned to an exact version; container-based tools (trivy, gitleaks, osv-scanner) pinned by image digest.
- `actions/checkout` with `persist-credentials: false`.
- No `pull_request_target`, no untrusted input interpolated into `run:` blocks. zizmor enforces this.
- Concurrency groups so a new push cancels the previous run on the same branch.

### Local runs

`make ci` runs the same jobs in the same order. Python tools run through `uv run`, front-end tools through `pnpm`, and trivy, gitleaks and osv-scanner run from the same digest-pinned container images CI uses, so the local results match CI. Docker is the only host prerequisite besides uv and pnpm. Individual targets: `make lint`, `make test`, `make scan`, `make images`, `make e2e`, `make docs`.

### Gate policy (ADR-0005)

- No gate is disabled or loosened to pass a build.
- A suppression is allowed only in a tracked file (`.trivyignore.yaml` with an `expired_at` date, `# nosec BXXX: reason`, `# nosemgrep: rule-id reason`, `.gitleaks.toml` allowlist entries with a reason). Each one needs your approval in review.
- CI prints every active suppression in the job summary, and an expired suppression fails the build.

## Risks

- WeasyPrint versus distroless. WeasyPrint needs Pango, HarfBuzz and fontconfig, which a distroless image does not have. In M3 we will probably need either a separate renderer image built on a slim Debian base with the shell removed, or a larger app image. ADR-0002 will name this so it is not a surprise.
- FIPS. Distroless has no FIPS variant. The M5 "document running on FIPS-enabled base images" item will likely mean a second, documented build path (for example a UBI-based image), not a change to the default.
- Base-image CVEs with no fix available can block builds under a strict trivy gate. The suppression process in ADR-0005 handles this without loosening the gate, but it will cost some review time each month.
- Semgrep registry rules are fetched at scan time and carry their own license. That is fine for public CI; an air-gapped fork of the pipeline would need the rules vendored. Documented in ADR-0005.
- Keyless cosign writes to the public Sigstore transparency log, which records the repository and workflow identity. Fine for an open-source project. Air-gapped verification needs the signature bundle shipped with the image; the M5 air-gapped guide will cover it.
- The strict CSP (`style-src 'self'`) may conflict with some Radix or ECharts behavior. React sets inline styles through the CSSOM, which CSP allows, so I expect this to be fine, but I will confirm it when those components arrive in M2. The policy stays strict until then.
- The e2e job builds both images and runs a browser, so CI will take several minutes. Build caching through the GitHub Actions cache keeps it down; if it gets slow, e2e can run on pull requests to `main` only.
- osv-scanner lists `uv.lock` among its supported lockfiles, and I will confirm that on the pinned version during setup. If it does not parse our lock file, the job scans a requirements file exported with `uv export` instead, so coverage stays the same.
